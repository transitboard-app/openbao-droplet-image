# Audit — 2026-08-11

A hardening, security, optimization and correctness review of the appliance image, against commit
`651c42c`. This document is the record of what was found and how it was found, so each item could be
argued with before it was acted on.

**All of it has since been acted on**, and the fixes were verified in the same lab described below —
including a full unattended reboot with the store intact. Three things came out differently from what is
proposed here, and the differences are worth more than the agreements:

- **Finding 6's stated fix would have broken `mise run debug`**, and the debug build is gone anyway.
  Deleting the marker at the start of `build:image` deletes the file the `debug` task writes immediately
  before calling it, so that fix could not have been applied as written. What happened instead is that
  the whole capability was removed — the task, the flag, the marker, and the `setup.sh` block that
  unlocked root and wrote a `PasswordAuthentication yes` drop-in. A build path whose purpose is to defeat
  this image's authentication is a permanent invitation, and with no marker there is nothing left to
  leak into a release build. `verify-image` still asserts all three artifacts are absent; those checks
  now guard against reintroduction. The getty on `tty1` went with it, since no password can ever match.
- **Finding 3's "the existing `chronyd`-adjacent cron" does not exist.** Nothing in any runlevel ran a
  scheduler. Bounding the audit log therefore meant enabling `crond`, which is a real decision and is
  argued in `image/setup.sh`. Upstream settled the mechanism: the `file` audit device "does not currently
  assist with any log rotation", and a `SIGHUP` makes it close and reopen. Measured here: the signal
  recreates `audit.log` immediately, before any request. `log_file` with `log_rotate_bytes` was rejected
  after measurement — it writes *in addition to* stderr rather than instead of it, so it adds a bounded
  fourth file beside an unbounded second one.
- **A defect this audit did not reach.** `alpine-make-vm-image` reports a failed chroot script as
  `ERROR: Script failed` and still exits 0. The build then compacted the half-hardened image and
  `build:assert` passed it, because a partial image still contains the 186 MiB `bao` binary and clears
  the 200 MiB floor. Neither the exit code nor the size could tell a fully hardened image from one that
  stopped after `==> installing OpenBao`. `setup.sh` now stamps the stage directory as its last act and
  `build:assert` refuses an image without it.

- **Finding 4's fix was the right instinct in the wrong place.** Copying `cloud-ssh-keys`' retry loop
  into `openbao` fixes the instance and preserves the cause: two services independently polling the
  metadata service, which is exactly how one of them ended up with fifteen attempts and the other with
  one. The loop now lives in a single `metadata` service that caches to `/run/metadata` and `provide`s a
  virtual; `cloud-ssh-keys` and `openbao` declare `need metadata` and read files, and neither contains a
  URL. The wait itself cannot become a dependency — `need net` means an interface is configured, and the
  metadata service is not a service on this machine. The Raft volume mount moved out of `start_pre` for
  the same reason: a volume that will not mount is now reported as a volume that will not mount, rather
  than as OpenBao failing to start.

Two smaller notes. Finding 1's fix needed no AppArmor change at all — the ownership was the whole
problem, and the profile already granted `/etc/openbao/** r`. And finding 8's module list left
`net/mptcp` in place, which is autoloadable on a `socket()` call by the same argument as the families it
does remove; it was left because it is outside what this audit examined, not because it was judged safe.

The image under review: Alpine 3.24, kernel 6.18.44-0-virt, OpenBao 2.6.1 (Go 1.26.5), 104 packages.

## Method

Two passes, because they answer different questions.

**Offline.** The built qcow2 was mounted through `qemu-nbd` on a linux-x64 host and read directly —
permissions, module tree, kernel command line, package database, `/etc/shadow`, symlinks.

**Live.** The image was booted under QEMU against a faked DigitalOcean environment, and OpenBao was
initialized, unsealed and used. This is the pass that produced most of the findings, and it is the pass
[`AGENTS.md`](../AGENTS.md) says had never been run: *"Nothing has read from OpenBao through this image
yet."* The fake environment was three things:

- a SCSI disk presenting as vendor `DO`, model `Volume`, so `start_pre()` finds a Raft volume the way it
  does on a Droplet — `qemu-system-x86_64 -device scsi-hd,vendor=DO,product=Volume`
- a metadata service on `169.254.169.254`, reached through QEMU's `guestfwd` in its per-connection
  `cmd:` form; the chardev form multiplexes every guest connection onto one stream and answers about two
  requests before going silent
- two interfaces, `eth0` and `eth1`, so the two-NIC arrangement the image is built for came up rather
  than the single-NIC case QEMU usually gives it

Under that, OpenBao reached `Initialized true / Sealed false`, served KV v2 reads and writes, wrote a
policy, enabled AppRole and minted a token against it, wrote audit records, and reported itself Raft
leader.

## Findings

Ordered by what they cost, not by how hard they are to fix.

### 1. The `bao` CLI is confined by the server's profile, so no operator command works on the node

An AppArmor profile attaches to a path. `profile openbao /usr/sbin/bao` therefore confines **every**
execution of that binary, including the one an operator runs by hand — and the profile grants no
capability of any kind. `/etc/openbao/tls` is mode 0700 owned by uid 65532, so root needs
`CAP_DAC_READ_SEARCH` to traverse it, and does not have it:

```
$ bao status
failed to read environment: Error loading CA File: open /etc/openbao/tls/ca.crt: permission denied

apparmor="DENIED" operation="capable" profile="openbao" comm="bao" capname="dac_read_search"
apparmor="DENIED" operation="capable" profile="openbao" comm="bao" capname="dac_override"
```

There is no CA path that works. `/root/ca.crt` is refused by the profile's own `audit deny /root/**`,
and `/tmp/ca.crt` by omission. `-tls-skip-verify` succeeds, which is worse than failing, because it is
the workaround an operator will reach for and it turns off certificate verification on the host holding
every production credential.

This breaks `bao status`, `bao operator init`, `bao operator unseal`, `bao kv` and the rest — including
the first-boot procedure in [`README.md`](../README.md).

**Fix, verified.** Give the directory to root and let the openbao group read it, in `image/setup.sh`:

```sh
install -d -o root -g "$BAO_GID" -m 0750 /etc/openbao/tls
```

with the key `0640` and the certificates `0644`, both `root:openbao`. Measured on the running appliance:
the server still reads its key through the group, and `bao status` from root then works with
`BAO_CACERT` set. `README.md`'s `chown 65532:65532 /etc/openbao/tls/*` becomes `chown root:openbao`.

This is worth doing for a second reason. Today the uid OpenBao runs as owns the directory holding its own
private key, so if AppArmor ever fails open — the failure mode this repository is most careful about —
the process can rewrite its own TLS material. Under the fix it cannot, whatever AppArmor is doing.

### 2. A Raft snapshot cannot be taken on the node at all

Every destination an operator would choose fails:

```
bao operator raft snapshot save /root/snapshot.bao        apparmor="DENIED" operation="mknod"
bao operator raft snapshot save /tmp/snapshot.bao         apparmor="DENIED" operation="mknod"
bao operator raft snapshot save /var/lib/openbao/snap.bao Error taking the snapshot: permission denied
```

The first is the profile's `audit deny /root/** rwklx`. The second is denial by omission. The third is
not AppArmor at all but DAC: the directory is 0700 owned by 65532 and the confined CLI runs as root
without `dac_override`.

[`image/overlay/etc/openbao/openbao.hcl`](../image/overlay/etc/openbao/openbao.hcl) says the daily
snapshot is *"the entire availability story"* while there is one node. It currently has no working path
on the node.

**Fix.** Either grant a snapshot directory that root can write while confined — a root-owned
`/var/backups/openbao` with an explicit `rw` rule — or state in `README.md` that snapshots are taken off
the node through the `openbao:tunnel` forward, where the CLI runs unconfined. The second is probably
right, but it has to be written down, because the obvious command fails with a permission error that
reads like a bug.

### 3. Nothing rotates the audit log, and a full root filesystem is an outage

There is no `logrotate` binary in the image. The three files in `/etc/logrotate.d/` came in with other
packages and do nothing. `audit.log`, `stdout.log` and `stderr.log` grow without bound.

Measured on the running appliance: 20 `bao kv get` operations added 115,867 bytes to `audit.log` —
**5.8 KiB per operation**, or about 477 MiB/day at one operation per second.

The consequence is stated in the config file itself: OpenBao refuses requests when every audit device
fails to write. Putting the audit log on the Droplet's own disk keeps a full log from taking out the
Raft volume, but it does not stop a full root filesystem from taking out the service. The smallest
Droplet has 25 GiB.

**Fix.** Bound the file. Adding `logrotate` reintroduces a scheduler and a package; the cheaper option is
OpenBao's own `file` audit device rotation options, or a `size`-triggered rotation run from the existing
`chronyd`-adjacent cron. Whichever is chosen, the appliance should not be able to fill its own root disk.

### 4. `openbao` reads its private address from the metadata service once, with no retry

[`image/overlay/etc/init.d/openbao`](../image/overlay/etc/init.d/openbao) makes a single attempt:

```sh
address="$(wget -qO- -T 5 http://169.254.169.254/metadata/v1/interfaces/private/0/ipv4/address ...)"
```

Observed on a boot where everything else came up correctly:

```
 * Installing pod routes ... [ ok ]
 * Mounting Raft volume /dev/sda ... [ ok ]
 * Could not read this node's private address from the metadata service.
 * ERROR: openbao failed to start
```

`cloud-ssh-keys` retries fifteen times for exactly this reason, and says so: *"the network is up" and
"the metadata service answers" are not the same instant.* OpenRC does not retry a failed `start_pre`, so
the node finishes booting healthy, answers on port 22, and has no secret store.

That defeats the reason the service is enabled at boot in the first place. `image/setup.sh` argues that a
store which stays down after an unattended reboot is the worse failure — and this is the path that
produces exactly that.

**Fix.** Retry the metadata read the way `cloud-ssh-keys` does.

### 5. The OpenBao binary is not checksum-verified

`[tools]` pins `github:openbao/openbao = "2.6.1"` with no `checksum`, and there is no `mise.lock`
(`mise settings get lockfile` reports it unset). The `http:alpine-make-vm-image` entry beside it does
carry a checksum, which makes the gap easy to miss.

`bao_sha256` in `[vars]` is never compared to anything. It is interpolated into `.build/stage/provenance`
as the string `upstream <sha>`, so a tampered download would be recorded with the checksum it failed to
match. Two comments assert a verification that does not happen — `mise.linux-x64.toml` (*"mise verified
the download against a pinned checksum before any of this ran"*) and `image/setup.sh` (*"the checksum
mise verified the download against"*).

This is the whole payload of a secret store, fetched over the network on every build.

**Fix.** Compare before stripping, in `stage:payload`:

```sh
test "$(sha256sum "$(command -v bao)" | cut -d' ' -f1)" = "{{ vars.bao_sha256 }}"
```

Enabling mise's lockfile is the better long-term answer; the one-line assertion is what makes the
existing comments true today.

### 6. `mise run debug` can silently turn the next release build into a debug image

`stage` declares `sources = ["image/**/*"]` and `outputs = [".build/stage/setup.sh"]`, so mise skips it
when nothing under `image/` has changed. `debug` writes `.build/stage/debug-password` and removes it only
after `build:assert` succeeds. If the debug build is interrupted or fails before that, the file survives,
`stage` is skipped on the next run, and `mise run build` produces a password-authentication image under
the release filename.

Reproduced with a minimal config:

```
--- second run, image/ unchanged ---
[stage] sources up-to-date, skipping
--- does the stale file survive? ---
-rw-r--r-- debug-password
-rw-r--r-- setup.sh
```

`verify` catches it through `check "root has no password"`, but `verify` is a separate task and not a
dependency of `build`. Only the release workflow runs both.

**Fix.** Delete the marker at the start of `build:image` rather than at the end of `debug`, and have
`verify-image` assert the two artifacts a debug build leaves behind — `/etc/APPLIANCE-DEBUG` and
`/etc/ssh/sshd_config.d/00-debug.conf` — rather than inferring it from `/etc/shadow` alone.

### 7. `libcap-utils` is unused, and ships `setcap` and `capsh`

[`image/packages`](../image/packages) justifies the package as *"getpcaps, used by the boot-time
self-check to prove OpenBao actually holds CAP_IPC_LOCK"*. That reason is gone twice over: the capability
was removed, and `openbao-selfcheck` reads `CapEff` out of `/proc/<pid>/status` with `awk`. Nothing in
the image references `getpcaps`.

What the package does put on the appliance is `/usr/sbin/setcap` and `/usr/sbin/capsh` — a tool for
granting file capabilities and a tool for manipulating capability sets — on a machine whose entire
premise is that nothing holds a capability. Removing the package drops all four files, including
`libcap.so.2`.

This is the rule in `AGENTS.md` applied to its own package list: prefer removing a package to adding one.

### 8. Module pruning misses the protocol families that autoload on a `socket()` call

`image/setup.sh` removes filesystems, netfilter, sched, sctp, 9p, ceph, sunrpc and bridge, with the right
reasoning: a module that is not on disk cannot be autoloaded by anything that provokes the kernel into
trying. The same reasoning has not been applied to the rest of `net/`. Still present:

| Path | What it is |
| --- | --- |
| `net/key` | PF_KEY, reachable with `socket(AF_KEY, ...)` |
| `net/llc`, `net/802` | LLC, reachable with `socket(AF_LLC, ...)` |
| `net/vmw_vsock` | vsock, seven modules |
| `net/l2tp` | L2TP tunneling, six modules |
| `net/openvswitch` | the OVS datapath |
| `net/mpls`, `net/nsh`, `net/ife` | encapsulation this appliance does not speak |

`drivers/` has the same gap. `drivers/nvme` was kept deliberately, because DigitalOcean's storage
presentation is not guaranteed to stay virtio-blk — but that kept `nvme/target` as well as `nvme/host`,
and `nvmet-tcp` is the NVMe-over-TCP **target**: a network-facing block protocol server. `drivers/vhost`
and `drivers/vdpa` are the host side of virtio, useless in a guest. `drivers/hv` is Hyper-V.

`arch/` is not pruned at all, and this one is not hypothetical. On the running appliance:

```
kvm_amd               139264  0
kvm                  1384448  1 kvm_amd
```

1.4 MiB of hypervisor loaded itself into the secret store host. `arch/x86/kvm` holds `kvm.ko`,
`kvm-amd.ko` and `kvm-intel.ko` and should go with the rest.

### 9. `openbao-selfcheck` never runs on its own, and operator use permanently fails it

`image/packages` and `AGENTS.md` both call it "the boot-time self-check". There is no init script for it
and no `rc-update` line; the boot runlevels contain `apparmor`, `bootmisc`, `hostname`, `hwclock`,
`modules`, `net.lo`, `seedrng`, `swap`, `sysctl`, `syslog` and `tiny-cloud-boot`, and the default
runlevel contains no self-check either. It runs when a human types it, which is the one case where a
check is least needed.

There is a second problem underneath that. The script greps all of `dmesg` for denials, and because of
finding 1 every `bao` command an operator runs logs `dac_override` and `dac_read_search` denials. The
self-check went from fully green to reporting *"the profile is too tight somewhere"* purely because
somebody used the CLI. A check that a normal operation permanently breaks stops being read.

**Fix.** Scope the denial search to the server's pid, or to `class="file"` denials with `fsuid=65532`,
and run it at the end of boot so its output lands on the serial console DigitalOcean's recovery console
shows.

## Hardening that is ready to enable

`AGENTS.md` lists both of these as untested, with the note that each can prevent boot and should be added
one at a time with a boot test. Both were added one at a time and boot-tested here.

**`module.sig_enforce=1`.** Booted clean. `/sys/module/module/parameters/sig_enforce` reads `Y`, Alpine's
own signed modules load normally, and a tampered module is rejected:

```
insmod: ERROR: could not insert module /tmp/m.ko: Key was rejected by service
```

This is what turns finding 8 from a measure against autoloading into a measure against an attacker with
root. The kernel already sets `CONFIG_MODULE_SIG_ALL=y` and carries Alpine's key, so nothing else is
needed.

**`lockdown=integrity`.** Booted clean. `/sys/kernel/security/lockdown` reads
`none [integrity] confidentiality`. OpenBao unsealed, served a KV read, and `openbao-selfcheck` returned
fully green with no denials. `lockdown` is already in the `lsm=` list; only the mode was missing.

## Correctness and documentation

**`README.md` is wrong in a way that would cause a regression.** It still opens by saying the appliance
exists so OpenBao can *"lock its memory"* and that *"the capability is granted ambiently and
`openbao-selfcheck` proves the pages are locked"*. The operating section says the self-check asserts
*"`VmLck` is non-zero, `CAP_IPC_LOCK` is held"*. The status section says *"Root's password is locked"*.
All three are the exact mistakes `AGENTS.md` was written to stop somebody making again.

**`verify-image` detaches every loop device on the host.** Its EXIT trap runs `losetup -D`, which is
"detach all", not "detach mine". On an Ubuntu CI runner or a developer machine that reaches loop devices
the script did not create. It should be `losetup -d "$loop"`.

**`verify-image` is missing three assertions** for properties that are correct today and unguarded:

- no `/etc/ssh/ssh_host_*` baked into the image. Confirmed absent, and confirmed generated at first boot
  (`ssh-keygen: generating new host keys: RSA ECDSA ED25519`). A build that ever started `sshd` in the
  chroot would give every Droplet the same host key, and nothing would say so.
- `sysctl` enabled in the boot runlevel. All twenty settings in `99-openbao.conf` depend on it, and it is
  in that runlevel only because Alpine puts it there.
- the debug-build artifacts, per finding 6.

**`image/packages`** says blank lines and comments are stripped by `scripts/build-image`. There is no such
file; it is the `build:image` task in `mise.linux-x64.toml`.

**`openbao-pod-routes`** returns from `start()` inside the `while` loop, so a bad route line skips the
matching `eend` and leaves the `ebegin` dangling.

**`cloud-ssh-keys`** matches `^(ssh-|ecdsa-)` in its user-data fallback, which misses
`sk-ssh-ed25519@openssh.com` and `sk-ecdsa-sha2-nistp256@openssh.com` — the FIDO key types.

**supervise-daemon gives up after five crashes.** Alpine's `/etc/rc.conf` defaults are
`respawn_delay=2`, `respawn_max=5`, `respawn_period=1800`, and the service does not override them. Five
crashes in thirty minutes and the store stays down until somebody notices. That may well be the right
behavior, but it is currently inherited rather than chosen, and the image already edits `rc.conf` for
`rc_depend_strict`.

**Smaller things.** `bao_sha256` and its comment are spliced into the middle of the `image_size` comment
block in `mise.linux-x64.toml`. `/boot/extlinux.conf.old` and `/boot/config-6.18.44-0-virt` survive into
the image. Six gettys run on `tty1` to `tty6` for an appliance with no keyboard. `bao` is a non-PIE `EXEC`
binary, so its own text is not subject to ASLR — upstream's build choice, not fixable here, but worth
knowing next to `randomize_kstack_offset=on` on the kernel command line.

## Confirmed working

Recorded because several of these were open questions in `AGENTS.md`, and a negative result is only
useful if the positive ones are written down beside it.

**The AppArmor profile is correct for the server.** Across `operator init`, `operator unseal`, enabling
KV v2, writing and reading a secret, writing a policy, enabling AppRole, minting and using an AppRole
token, the file audit device, Raft leader election, and a full stop/start with the store intact — **zero
denials**. The one open question in `AGENTS.md` about whether the profile is tight enough for real use is
answered for everything except the PostgreSQL engine reaching a live database.

**The database secrets engine loads in process.** This was the largest remaining risk, because
Vault-lineage database plugins have historically run as subprocesses and the profile denies all exec.
OpenBao 2.6.1 does not fork: configuring `postgresql-database-plugin` produced no exec denial and failed
with `dial tcp 10.0.2.2:5432: connect: connection refused`, which also shows outbound TCP reaching
`connect()` from inside the profile. Separately, a confined `bao` completed a TLS handshake against a
public HTTPS host, so `abstractions/ssl_certs` and `abstractions/nameservice` cover certificate
verification and DNS.

**The `/sys/fs/cgroup/**/cpu.max` rule works.** A server started under the current profile produces no
cgroup denial. The image in `out/` predates the rule and still shows the Go GOMAXPROCS denial, which is
what made this worth checking.

**The sysfs volume detection works.** `Mounting Raft volume /dev/sda ... [ ok ]`, with the vendor and
model read from `/sys/block/sd*/device/`, on a disk that has no `/dev/disk/by-id` entry.

**Everything else that was checked and is correct.** Every sysctl sampled was applied — eleven of the
twenty, covering all of the `kernel.*` and `fs.*` settings. AppArmor enforcing and
the process confined, running as uid 65532 with `CapEff` all zero and `no_new_privs` set. No swap. Zero
setuid or setgid files. No world-writable files. No file capabilities. No baked SSH host key and no baked
RNG seed. Root's password field is `*` and not `!`. Root filesystem expansion works. `SIGTERM` reaches
the confined process and the store survives a restart. `shellcheck --severity=warning` is clean over
every script the image ships.

## Not covered

- OpenBao minting credentials against a real PostgreSQL instance. The plugin was shown to load and to
  reach `connect()`; no database was stood up behind it.
- Agent sidecar injection from a Kubernetes cluster.
- The pod routes carrying real traffic. `openbao-pod-routes` was shown to install a route; nothing came
  back along it.
- Anything specific to DigitalOcean's own BIOS, metadata service or volume attachment. The lab imitates
  all three and is not a substitute for any of them.
